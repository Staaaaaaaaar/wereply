# Linux 个人微信好友私聊自动回复调研

调研日期：2026-10-25。需求：个人微信好友私聊，主要在 Linux 使用。

本文结合上游文档、已发布版本源码和本机只读环境检查。上游声称的能力不等于本机验证结果；没有登录测试账号、提取密钥、运行机器人或发送微信消息。

## 结论

可以实现，但接入层决定可用性。当前没有在本次调研中核实到腾讯面向普通开发者提供的、能直接读取并代回个人号既有好友私聊的通用开放接口。不要将公众号、微信客服、企业微信机器人或 ClawBot/iLink 的能力直接套用到这个需求。

建议依次推进：

1. 在当前 Linux 原生微信上验证 AT-SPI 无障碍读取与 X11 发送，先只处理少量明确授权的联系人、纯文本和固定回复。
2. 如果能可靠读取消息方向、会话身份和消息顺序，继续做轻量本机工具；如果这些基础条件不成立，就停止扩展该原型。
3. 如果需要独立后台运行、不占用日常桌面，再验证隔离的 Xvfb/容器微信。已有项目可借鉴，但有些同时读取进程内存和解密消息数据库，必须接受这一技术边界才能采用。
4. 暂不把直接实现微信协议、Windows DLL Hook 或购买不透明协议服务作为首版基础。

这是针对个人自用、少量私聊的工程选型建议，不是对长期在线、平台授权或账号安全的保证。

## 方案对比

以下可靠性与成本是工程判断，没有经过统一基准测试；不能据此推导封号概率。

| 路线 | 能否覆盖好友私聊 | Linux 适配 | 主要约束 | 本项目建议 |
| --- | --- | --- | --- | --- |
| 公众号 / 微信客服 | 不能直接接管个人好友会话 | 后端可部署 Linux | 用户入口与账号身份改变 | 排除为主路线 |
| ClawBot / iLink | 未核实具备代回既有好友的能力 | 适合 Linux 服务 | 扫码绑定 Bot 与接管好友列表是不同能力 | 不作为本需求接入层 |
| 原生微信 + AT-SPI + X11 | 原理上可以，需验证消息控件 | 本机适合验证 | 控件暴露、切换会话、焦点及人工操作冲突 | 首先验证 |
| 原生微信 + OCR / 视觉识别 | 可以尝试 | 更适合受控 X11 桌面 | 识别错误、内容截断、方向判断、重复消息 | 作为受限补充 |
| 数据库读消息 + UI 发消息 | 有开源实现可参考 | Linux 可实现 | 内存密钥、版本依赖、数据库变化、发送串行 | 后台需求的候选 |
| 原生协议实现 | 有开发中项目 | 有 Linux 实现 | 登录、续期、同步和服务端兼容性 | 暂不作为首版 |
| wxauto / Windows Hook | Windows 端有实现 | 需要 Windows 中转端 | 客户端版本、维护、VM、部分方案涉及注入 | 备选 |
| Web 微信 / ItChat | 取决于账号能否登录 Web 微信 | 脚本可跑 Linux | 上游长期有无法登录报告 | 不优先 |
| Android 通知桥 | 仅在通知及快捷回复满足条件时 | Linux 可做回复服务 | 手机配套、通知缺失或合并、快捷回复能力 | 条件性备选 |

## 为什么 iLink 目前不能直接解决你的需求

腾讯确实有 [Tencent/openclaw-weixin](https://github.com/Tencent/openclaw-weixin)，不是所有“微信接入 AI”都是第三方逆向。

但这里需要回答的是：它是否把你个人微信里好友发来的消息交给程序，并允许以你的身份回复？本次没有核实到这一能力。

官方仓库描述扫码、Bot 收发与渠道集成；协议文档也强调客户端字段不能代表完整服务端契约。出现 `to_user_id`、`context_token` 或 direct chat 标记，均不足以证明接管个人好友私聊。

此外，[wx-bot](https://github.com/lawrencewzen/wx-bot)明确说明只理会扫码者本人、不支持好友。它说明一种已知实现的限制，不能据此断言未来所有 iLink 产品的能力，但足以排除“装好该工具就能代回好友”的推荐。

依据：[腾讯插件说明](https://github.com/Tencent/openclaw-weixin/blob/main/README.zh_CN.md)、[协议范围说明](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol_zh_CN.md)。

公众号、微信客服和企业微信属于其他产品入口。若未来接受改变聊天入口，可以另行选型；当前不应把它们的回复窗口、条数或权限规则套用到个人好友会话。本次部分微信官方文档站无法访问，没有据二手转载对具体配额作当前确认。

## 建议实现结构

下面是本项目的设计建议，不是上述某个项目已具备的功能清单。

```text
Linux 微信接入器
    │ 规范化入站事件
    ▼
消息收件箱与去重 ──→ 私聊/联系人白名单/时段/人工接管判断
                              │
                              ▼
                      固定规则或模型生成候选回复
                              │
                              ▼
                       持久化待发送任务
                              │
                              ▼
                    串行发送与结果核对
```

回复服务与接入器分离。以后从本机 UI 换成隔离容器，规则、上下文和消息处理逻辑尽量不重写。

第一版建议 Python + SQLite；配置使用 TOML 或 YAML 二选一。先做 CLI 和日志，跑通核心链路后再选择桌面托盘或本地管理页。是否使用 FastAPI、PySide6、异步模型客户端，取决于最终交互与接入接口，不需要现在全部引入。

### 接入器的最低要求

接入器至少提供：健康状态、增量取消息、发送文本和查询发送结果。能力检查需要分别说明：能否识别稳定会话 ID、是否有可靠消息 ID、能否判断自己发的消息、是否提供发送回读证据。

内部事件建议包含账号、会话、发送者、方向、消息类型、来源时间、观察时间和原始消息标识。没有真实 ID 的 UI/OCR 后端必须显式说明，只能使用会话、方向、可见消息顺序和窗口内容做保守去重，不能与数据库 ID 等价。

如果只有昵称，无法排除同名联系人，必须先建立明确的会话绑定；发送时重新确认目标，无法确认就暂停。

### 去重与发送状态

优先使用 `(account_id, conversation_id, source_message_id)` 作为持久去重键。不要仅用消息文字的哈希：同一个人连续发两次“好的”是两条不同消息。

启动时建立处理起点，默认不自动回复已有历史；重启时恢复已接收但未处理的事件，并对过期任务设置截止时间。

收件箱和待发送任务使用事务。发送状态至少分为：未发送、已提交、已观察到本机消息记录、失败、结果不确定。界面点击成功不等于对方收到；本机消息回读也不等于远端送达回执。

遇到发送后超时，要先查证再决定是否重试。UI 操作一般无法提供严格 exactly-once 保证；若无法确认，保留“不确定”状态并暂停该任务，避免盲目重发。

### 并发与人工接管

同一微信界面的操作只允许一个发送执行器。可以并发生成不同会话的回复，但选择会话、输入、发送与回读必须串行完成。

同一联系人连续发多条短消息时，可采用短暂合并窗口统一回复。发送前重新检查：是否已有更新消息、用户是否手动回复、任务是否过期、会话是否仍正确。

建议提供全局暂停、联系人暂停和明确的人工接管模式。手机人工回复能否被及时检测必须验证，不能只依赖本机鼠标或键盘活动。

### 规则与 AI

先把“收到白名单好友文本 → 回复一条固定文本”做稳定，再接模型。首版只做文本，群聊、付款、文件和语音可先忽略或留待人工处理。

后续按联系人隔离上下文。固定规则优先，模型超时使用有限的兜底策略，避免每轮错误都回复一条报错。入站聊天只作为回复素材，模型不能据聊天内容修改白名单、执行 shell、读取任意文件或自行选择其他收件人。

本地模型与云端模型都可接入；本地节省外发内容，云端更省本地算力。具体模型、价格与硬件需求应在接入验证通过后另做比较。

## Linux 运行细节

### AT-SPI、X11 与视觉识别

[AT-SPI 文档](https://docs.gtk.org/atspi2/)提供应用无障碍对象访问能力，但目标微信是否完整暴露聊天内容，需要当前版本实测。优先读控件文本与结构；只在缺失区域使用 OCR。不要把“界面可截图”当成“消息能稳定结构化”。

[xdotool 上游](https://github.com/jordansissel/xdotool)明确其基于 X11，且不能在 Wayland 下正常完成所有功能。本机当前是 X11；未来迁移 Wayland 必须重新评估窗口激活、截图、剪贴板和输入路径。

纯视觉方式需要固定窗口布局、缩放和主题，处理消息气泡方向、滚动和截断。视觉模型输出也必须经过目标与消息一致性检查，不能直接让模型决定在哪个会话点击发送。

### 本机桌面和隔离桌面

本机模式适合先验证，但会与日常使用争用焦点及剪贴板；锁屏、最小化、休眠和手动切换都有可能影响流程，必须测试。

Xvfb 模式把微信放进独立图形会话，可减少与日常桌面的冲突，但需要同时维护 D-Bus、无障碍服务、字体、显示与登录状态。服务器可以没有物理显示器，但 UI 路线仍需要虚拟图形会话。

容器中的微信会成为额外桌面登录实例；它与本机微信、手机之间是否存在互踢或同步差异，要用真实账号验证，不能提前保证。

### 数据库路线

数据库监听比 OCR 更容易拿到结构化身份与顺序，但难点包括密钥获取、消息分库、新分片、WAL 一致性、schema 变化和重登录后的失效。

文件变化通知只应作为“可能有新数据”的触发器，不能当成完整消息事件。需要补充增量扫描与高水位检查，也不能直接修改微信数据库来模拟发送。

如采用上游容器，固定并记录 CLI、服务、镜像 digest、微信版本与配置。固定版本方便复现，后续仍需要验证升级兼容性。

## 账号与内容边界

没有证据可以支持“低频不会封号”或“模拟点击就是零风险”。降低操作频率有助于减少误操作与骚扰，但不是平台授权或免风控依据。

对本项目更实际的约束是：只允许白名单私聊、控制每会话与全局回复量、异常时暂停、默认不处理历史、不自动添加好友或群发。自动化状态应容易看见和关闭。

如果使用进程密钥路线，密钥和解密内容属于敏感本地数据；如果使用云端视觉，截图还可能含其他会话列表，外发范围比单条消息更大。API 与 VNC 建议仅绑定本机，凭证不进 Git，调试日志默认不保存完整聊天或密钥。

## 分阶段验证与验收

下面是建议的开发安排和验收目标，不是已完成的测试结果，也不是上游 SLA。

### 阶段 0：接入可行性，预留半天至两天

1. 固定本机微信版本，检查无障碍树能否区分会话、消息、方向与输入框。
2. 先用文件传输助手验证中文、多行、表情的输入与发送；这一步不能替代好友私聊验证。
3. 用两个同意参与测试的好友会话，验证同名、消息连发、切换会话和自己回复。
4. 如果无法可靠区分消息或目标，停止自动发送，评估隔离后端。

### 阶段 1：固定规则自动回复，预留两至四天

只处理少量白名单好友的纯文本。实现持久去重、串行发送、暂停、任务过期、人工接管和异常停机。先验证正确性，再优化延迟。

### 阶段 2：后台部署与稳定性，预留三至七天

仅在需要时引入 Xvfb/容器。检查掉线、断网、进程重启、主机休眠与磁盘写入失败。维护成本往往集中在这一步。

### 阶段 3：可选 AI 与界面

增加会话隔离的模型回复、上下文限长、本地配置与发送记录。不要用 AI 效果掩盖接入层的漏消息或发错会话问题。

### 建议验收集

| 情况 | 期望行为 |
| --- | --- |
| 连续两条相同文本 | 识别为两条消息，不因内容相同错误去重 |
| 两个好友同时来消息 | 会话与上下文隔离，发送不串线 |
| 好友连续发多条短消息 | 合并策略可解释，无重复触发 |
| 自己从手机或电脑回复 | 按接管规则取消或暂停待发任务 |
| 程序重启 | 不把历史消息作为新消息回复 |
| 发送操作后服务超时 | 先核对，不盲目重试 |
| 非白名单、群聊、非文本 | 不进入首版自动回复流程 |
| 微信掉线或界面变化 | 暂停发送并明确报告原因 |
| 锁屏、最小化和桌面切换 | 行为经过实测，失败时不会发错对象 |

可设定首轮目标：至少 100 条受控私聊测试消息，错会话 0、重复回复 0，并记录漏收与发送不确定数量；再做 24 小时观察。通过只能说明该账号、该客户端版本及该环境的结果，不能推导任意账号长期稳定。

## 其他备选与当前未决问题

Android 配套端可以监听通知并将文本交给 Linux 回复服务；只有微信实际暴露通知内快捷回复动作时，才可能通过相应动作回传。Android 的 [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService) 和[通知内回复能力](https://developer.android.com/develop/ui/compose/notifications/create-notification)只是系统机制，不能证明指定微信版本具备所需条件。通知关闭、消息合并、手机后台限制等都会影响覆盖，因此暂不优先。

后续实施前需要确定：

- 是否接受只在已登录桌面会话中运行，还是必须常驻后台。
- 是否接受读取进程内存密钥；若不接受，只能在 UI/通知等其他路径内取舍。
- 先做固定回复还是 AI 回复；二者可以共享接入与调度层。
- 微信当前版本是否能暴露足够的无障碍文本与身份信息。

截至本次调研，最值得先做的是最后一项验证。它成本较低，且能决定是否需要引入数据库、容器或其他端侧组件。
